## What was broken, and what it turned out to be

**1. Members saw `slates: []` on `/api/optimizer/slates` despite `slatesAvailable: 3`.**
Root cause: `filterSlatesForCurrentViewer` consulted the legacy `slate_status` table even when canonical Postgres served the list; canonical's promotion never writes that table. Fixed before this file's window began (`4b6b9e1`).

**2. `/dashboard` populated research-fed tiles (games, environment, stacks) but every DK-dependent tile was blank** (Vegas Coverage, DK Players, Identity Resolved, Starting Pitchers, Team Readiness), and **Slate Readiness showed a fabricated "Lineups Confirmed 30/30"** while the banner correctly said 15 games had no posted lineup.
Root cause, in two parts:
- `lib/slateReadiness.ts` defaulted a missing `dk_match_report_` document's `teams_awaiting_lineups` to `[]`, so absence of data computed as full confirmation. Fixed in `e3bf5e9`.
- `lib/slateContext.ts` (used by every `/dashboard/*` page) called `poolCache.listSlates` directly instead of going through `resolveServingBackend`, so every dashboard page — not just the Optimizer's own picker — was pinned to the legacy R2 path regardless of the canonical flag. Fixed in `6220439`.
- Even after that, the DK-dependent tiles stayed blank: `app/dashboard/page.tsx` read `dk_player_pool_`/`dk_match_report_` artifacts directly via `lib/loaders.ts`, and those two artifact types have had **zero writes in production object storage since at least 2026-09-06** — their writer (`build_dfs_pool_from_provider.py`) was superseded when eligibility/projections/ownership moved into canonical Postgres, and never re-wired into the automated refresh chain. Fixed in `bb290bc` with a canonical→legacy-shape adapter.

**3. The MLB worker (`scripts/run_mlb_dk_fetch_worker.ps1`) intermittently died with exit `3221225786` (`0xC000013A` / `STATUS_CONTROL_C_EXIT`)** on both the `railway run` (DK fetch) and `railway ssh` (research/eligibility/ownership) stages, with zero diagnostic output beyond "starting." **Root cause still unknown** — ruled out battery/idle/session-disconnect settings, confirmed no Defender/EDR detections, confirmed manual runs of the same command succeed. Hardened with full exception logging in `d87101f` so the next occurrence leaves a trail. Not touched again tonight.

**4. NFL wasn't loading at all.** Initial hypothesis (tonight's MLB serving-backend commits caused it) was **ruled out with certainty** — NFL's API routes (`app/api/nfl/*`) shell directly to Python via `runPythonScript`, zero imports of anything touched tonight. Real root cause: `GET /api/nfl/data?draftGroupId=153070` returned a bare 502 with DraftKings' own `ACCESS_RESTRICTED (HTTP 403)` — a live DraftKings call attempted from Railway's permanently-IP-blocked egress, because `nfl/pool_cache.py` fell through to a live call on any cache miss past 15 minutes, with no stale-but-usable tier. Fixed in `ef21597`.

**5. Only one NFL draft group (153068) ever got cached — the other four for the same slate date (153069/153070/153071/151307) never had.** Originally suspected to be the wrapper's 3-minute `ExecutionTimeLimit` truncating the fetch loop. **That theory was wrong.** Ran the real fetch manually outside the scheduler tonight (authorized production write) and found the actual cause in under a minute: `nfl/persistence.py::save_nfl_player_pool` built its file path as `dfs_input/nfl/<slate_date>/nfl_player_pool_<timestamp>.json` — no `draft_group_id` anywhere in it. `fetch_nfl_slates.py` computes one timestamp before its loop and reuses it for every draft group, so any two sharing a slate_date within one cycle collided on the *identical* path; the first one saved, everything after it hit `"Refusing to overwrite existing artifact"`. The real run took **39-48 seconds for all 6 discovered draft groups** — nowhere near the 3-minute limit, which had 3-4x headroom the whole time. Fixed in `f9f3046`.

**6. Even with real slate data loading, `mode: projection` (the mode anyone actually wants) failed for every draft group with zero coverage at every position (QB/RB/WR/TE/DST all 0).** Two layers here:
- The NFL identity crosswalk (DraftKings player → GSIS id, needed to look up real historical usage stats) had **zero rows** in production. `377d0d0` (2026-09-07) had added the refresh *script* but, by its own commit message, never actually run it against production credentials. Ran it tonight (authorized write): **851 rows, 54 seconds**, real per-position resolution (see below).
- **That fix made no difference — still 0/0/0/0/0 after the crosswalk was populated.** Diagnosed further: `historical_models/nfl_v1/inference.py::load_position_model` looks for trained model artifacts under `data/models/nfl/<position>/<version>/`, a bare local filesystem path never routed through the object-storage abstraction everything else in this codebase uses. That directory **does not exist anywhere** — not locally on this machine, not in git (`data/models/` is gitignored), and confirmed via `railway ssh` **not in the deployed container either**. `d9f0c37` ("NFL M10: train Big Money Native NFL projection models," historical) shows training happened once, but the resulting artifact was never committed or deployed anywhere durable, and no longer exists in any environment I could check. **Not fixed tonight — this is a real training/deployment task, not a quick fix, and wasn't attempted.**

**Partially, and not for the part that matters for actually winning.**

Neither was attempted tonight — this is a real project, not a bug fix, and needs a decision on how to prioritize it before Sunday.
