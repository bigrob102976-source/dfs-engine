## What was broken, and what it turned out to be

**1. Members saw `slates: []` on `/api/optimizer/slates` despite `slatesAvailable: 3`.**
Root cause: `filterSlatesForCurrentViewer` consulted the legacy `slate_status` table even when canonical Postgres served the list; canonical's promotion never writes that table. Fixed before this file's window began (`4b6b9e1`).

**2. `/dashboard` populated research-fed tiles (games, environment, stacks) but every DK-dependent tile was blank** (Vegas Coverage, DK Players, Identity Resolved, Starting Pitchers, Team Readiness), and **Slate Readiness showed a fabricated "Lineups Confirmed 30/30"** while the banner correctly said 15 games had no posted lineup.
Root cause, in two parts:
- `lib/slateReadiness.ts` defaulted a missing `dk_match_report_` document's `teams_awaiting_lineups` to `[]`, so absence of data computed as full confirmation. Fixed in `e3bf5e9`.
- `lib/slateContext.ts` (used by every `/dashboard/*` page) called `poolCache.listSlates` directly instead of going through `resolveServingBackend`, so every dashboard page — not just the Optimizer's own picker — was pinned to the legacy R2 path regardless of the canonical flag. Fixed in `6220439`.
- Even after that, the DK-dependent tiles stayed blank: `app/dashboard/page.tsx` read `dk_player_pool_`/`dk_match_report_` artifacts directly via `lib/loaders.ts`, and those two artifact types have had **zero writes in production object storage since at least 2026-09-06** — their writer (`build_dfs_pool_from_provider.py`) was superseded when eligibility/projections/ownership moved into canonical Postgres, and never re-wired into the automated refresh chain. Fixed in `bb290bc` with a canonical→legacy-shape adapter.

**3. The MLB worker (`scripts/run_mlb_dk_fetch_worker.ps1`) intermittently died with exit `3221225786` (`0xC000013A` / `STATUS_CONTROL_C_EXIT`)** on both the `railway run` (DK fetch) and `railway ssh` (research/eligibility/ownership) stages, with zero diagnostic output beyond "starting." **Root cause still unknown** — ruled out battery/idle/session-disconnect settings, confirmed no Defender/EDR detections, confirmed manual runs of the same command succeed. Overnight log analysis showed it's intermittent (17/17 research-stage attempts succeeded in one stretch; a separate 3-cycle run of total silence happened elsewhere) — not catastrophic, but real and unexplained. Hardened with full exception logging in `d87101f` so the next occurrence leaves a trail.

**4. NFL wasn't loading.** Initial hypothesis (tonight's MLB serving-backend commits caused it) was **ruled out with certainty** — NFL's API routes (`app/api/nfl/*`) shell directly to Python via `runPythonScript`, zero imports of anything touched tonight. Real root cause, found by testing progressively closer to the real request path (railway run → railway ssh in-container → real public HTTPS): `GET /api/nfl/data?draftGroupId=153070` returned a bare 502 with DraftKings' own `ACCESS_RESTRICTED (HTTP 403)` — a live DraftKings call attempted from Railway's permanently-IP-blocked egress, because `nfl/pool_cache.py` (unlike MLB's already-hardened `poolCache.ts`) fell through to a live call on any cache miss past 15 minutes, with no stale-but-usable tier. Fixed in `ef21597`.

## NFL single-draft-group gap — investigation only (per tonight's ask, not fixed)

**Does the fetch loop iterate over all discovered draft groups?** Yes. `scripts/fetch_nfl_slates.py::main()` calls `collector.collect_sport_universe("NFL")`, filters to Classic (`game_type_id == 1`), then does a plain `for s in slates: build_pool(...); save_nfl_player_pool(...)` over every one. No filter to "first" or "Featured only" anywhere in this script.

**Is the narrowing deliberate?** No — no comment, no filter, nothing restricting scope. It's incidental.

**Evidence it's a timeout/kill artifact, not a loop bug:** On 2026-09-07, when only 2 Classic draft groups were live for the relevant dates (153054, 151307), every single cycle in the log successfully saved *both* — full `slates_discovered: 2` with two `"status": "ok"` results, every ~5 minutes, for hours. Checked R2 directly tonight: **every one of the 12 retained pool files for 2026-09-13 is for draft group 153068** — none of the other four (153069, 153070, 153071, 151307) discovered on that same date have *ever* been cached, across 28+ hours of cycles. The number of live Classic draft groups for that date grew from 2 to 5 as the slate approached; the loop that worked fine at 2 has apparently never completed at 5.

This lines up with the wrapper's own failure mode already diagnosed for MLB and (differently) for NFL: `run_nfl_dk_fetch_worker.ps1` has **no internal timeout and does one synchronous blocking `& ... 2>&1` call** — if the 5-draft-group loop (live DK network call + structural validation + save + prune, ×5, sequentially) takes longer than Task Scheduler's `ExecutionTimeLimit=PT3M`, the whole process is killed externally *before* `main()` reaches its final `print(json.dumps(...))` — which exactly matches the "bare `run start`, then nothing" log pattern found across 28+ hours of NFL log history. Because saves happen progressively inside the loop (not batched at the end), whichever draft group is processed first survives; everything after the kill point is lost, every cycle. 153068 wins consistently, which is consistent with DraftKings' own API returning a stable order (not something this codebase sorts) and 153068 always occupying the first slot.

**If incidental, how big is the fix?** Not a missing loop — the loop already exists and is structurally correct. The likely fix is either (a) raising/removing the wrapper's `ExecutionTimeLimit` to fit 5 sequential live builds, (b) parallelizing the builds, or (c) at minimum porting the same async/timeout hardening from the MLB worker so a real timeout is diagnosed instead of silently truncating the loop — this is the same class of fix as queue item #2, not a separate one. Nothing downstream appears to assume "one pool per date" — `nfl/persistence.py`'s functions are already keyed by `(slate_date, draft_group_id)` pairs, and `nfl/pool_cache.py`'s `load_fresh_cached_pool` already takes an explicit `draft_group_id` to match against.

**Cost of fetching all five — reasoned estimate, not measured** (I didn't run the live script tonight; that would itself be a production write, out of scope for "investigate only"): each draft group's `build_pool()` call does one live DraftKings network round-trip (comparable slates elsewhere in this codebase run low-single-digit to ~20s depending on pool size — the Featured slate here is 744-917 players, notably larger than the others) plus in-memory validation (cheap) plus a save and a prune pass (each prune is a real R2 list+delete once past `DEFAULT_SNAPSHOT_RETENTION_COUNT = 12`, done once per draft group per cycle — a real but likely small addition, several R2 API round trips ×5 instead of ×1-2). Five sequential builds plausibly land anywhere from comfortably under 3 minutes to meaningfully over it depending on DK's response time that cycle — genuinely close to the boundary, which fits an intermittent-looking-total failure that's actually been *total* for this specific date the whole time. A real measurement needs either a live run or added timing instrumentation, neither done tonight.
